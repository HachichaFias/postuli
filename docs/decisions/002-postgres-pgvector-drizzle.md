# ADR 002 — PostgreSQL + pgvector through Drizzle ORM

- Status: accepted
- Date: 2026-09-27
- Scope: framing

## Context
The product needs relational data (accounts, profiles, opportunities, sources, saves, events),
hard-constraint filtering in SQL (RET-01), and optional semantic similarity on roles and skills.
The PRD recommends PostgreSQL + pgvector. Security requires parameterized queries only (PRD §13.7)
and versioned migrations (PRD §13.4).

## Decision
PostgreSQL 17 with the pgvector extension, accessed only through Drizzle ORM (`drizzle-orm` +
`postgres` driver), with migrations generated by `drizzle-kit` and committed under `drizzle/`.
Local development and tests run the `pgvector/pgvector:pg17` image through `docker compose`;
staging and production use a managed Supabase Postgres project (pgvector available). Each table
is created by the first story that needs it.

## Considered options
- Prisma — rejected because its pgvector support needs raw SQL escapes and its generated client
  adds a build step; Drizzle keeps SQL visible and types inferred from the schema.
- Raw SQL with `postgres` tagged templates only — rejected because agents would hand-write types
  for every table; the ORM gives one schema file as the source of truth.
- Railway Postgres — rejected for production because Supabase also hosts the CV storage (ADR 004),
  keeping one data vendor.

## Consequences
- Easier: one schema file (`src/server/db/schema.ts`) typed end to end; SQL-level hard constraints;
  pgvector available when s05 wants similarity.
- Harder: every schema change is a migration commit (kept separate from the story commit, as the
  method allows).
- Watch: Supabase region is outside Tunisia; law 2004-63 / INPDP review is required before a wide
  production launch (context §19.2).
